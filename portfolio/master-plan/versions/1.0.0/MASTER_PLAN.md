# Clover Master Plan 1.0.0

Preserved: August 17, 2026 · America/Chicago

## North star

Build one protected, portable, continuously improving knowledge and execution system that helps Chris Dortch understand, prioritize, build, operate, preserve, and improve his projects, legal work, resort operations, creative work, opportunities, and the people he is responsible for.

The system is **one brain, many representations**:

- a canonical knowledge and evidence layer;
- immutable raw sources;
- structured knowledge and project state;
- rebuildable search indexes;
- a durable decision and action ledger;
- portable exports and tested backups;
- multiple windows such as CloverApps, WarRoom, Companion, resort apps, and future OpenAI Sites.

No app, OpenAI Site, chat thread, deployment, database, or AI provider is allowed to become the only copy of important knowledge.

## Operating model

The system should work as follows:

1. Approved sources are inventoried and ingested with provenance.
2. The canonical layer preserves raw material and builds structured representations.
3. CloverApps and specialized windows present the relevant context.
4. AI identifies problems, opportunities, deadlines, dependencies, and next actions.
5. AI explains material consequences before an owner decision.
6. Safe, reversible work proceeds on isolated versions.
7. Deterministic systems perform repetitive verification.
8. Model judgment is used for interpretation, invention, difficult failures, and final review.
9. Irreversible actions require exact owner authority.
10. Every completed action returns a receipt and updates project, case, backup, and progress state.

## Non-negotiable boundaries

- Public resort data, operational guest/staff data, private legal evidence, personal/creative material, credentials, and financial records remain appropriately separated.
- Apps communicate only through necessary, documented, policy-approved relays.
- Imported content is untrusted data and cannot alter authority or policy.
- Secret values, customer records, private legal evidence, private communications, health information, and financial records do not belong in this public standards repository.
- Production merges, deployments, migrations, domain changes, purchases, messages, and sensitive data access require separate exact authority.
- A passing build or migration rehearsal is evidence, not release authority.
- Existing projects are protected until their identity, current production state, backup status, and rollback path are known.

## Program outcomes

### 1. Canonical Knowledge Hub, Window, and Vault

Create the protected knowledge foundation for ChatGPT history, Gmail, Drive, project repositories, deployment records, voice notes, scans, social sources, and approved external research.

Done means the raw sources are immutable, derived assertions retain provenance, indexes can be rebuilt, portable exports exist, and a clean-room restore has been demonstrated.

### 2. Verified portfolio inventory

Give every active, archived, or conceptual project one canonical ID and a record of its repository, deployment, domains, data stores, privacy class, latest verified version, owner decisions, backup status, and rollback anchor.

Unknown or contradictory records must remain visibly unresolved rather than being guessed.

### 3. Complete backup and recovery

Preserve full Git mirrors, readable source archives, deployment manifests, environment-variable names, encrypted data backups, object-storage inventories, checksums, and restore instructions. Prove recovery through periodic clean-room restore tests.

### 4. Safe build and release system

Use Clover Build Protocol for isolated branches, deterministic build/browser/accessibility checks, bounded visual review, exact preview identity, owner approval, production verification, and archived receipts.

### 5. Safe data-change system

Use Clover Data Change Protocol for disposable database rehearsals, synthetic fixtures, schema diffs, forward and corrective migrations, rollback, backup, restoration, reconciliation, and a separate production-data authority gate.

### 6. CloverApps and WarRoom control plane

Make CloverApps the owner-facing control plane over the canonical registry, projects, versions, previews, backups, decisions, and receipts. Make WarRoom the private evidence, case, deadline, strategy, and drafting window over permitted legal sources.

These windows may display and operate on the canonical knowledge layer, but they are not its sole copy.

### 7. Deliver the application portfolio

Stabilize and launch the applications that improve immediate income, resort operations, legal readiness, communication, creative distribution, and personal stability. Archive or consolidate duplicates only after preservation and owner review.

### 8. Continuous monitoring and Action Center

Monitor approved sources for deadlines, risks, anomalies, opportunities, and new evidence. Present human-only work as a clear Action Card. Completed work must update the ledger and percentage calculations.

## Execution phases

### Phase 0 — Truth and safeguards

- Maintain this master plan, current status, project registry, protocol pointers, and history.
- Reconcile conflicting project identities.
- Keep authority boundaries fail-closed.

Exit gate: future threads can determine the current plan and exact project state without relying on conversational memory alone.

### Phase 1 — Inventory and backup

- Inventory GitHub, Vercel, OpenAI Sites, domains, Drive, databases, storage, and relevant connected services.
- Build complete mirrors and evidence manifests.
- Restore-test low-risk projects first, then sensitive systems using encrypted lanes.

Exit gate: every important project has a verified backup and rollback anchor.

### Phase 2 — Canonical knowledge foundation

- Establish immutable source storage and structured knowledge.
- Ingest ChatGPT archive, Gmail, Drive, voice capture, scans, and approved sources incrementally.
- Add provenance, privacy classes, retention, and portable exports.

Exit gate: the knowledge layer can be rebuilt independently and searched with citations.

### Phase 3 — Control plane

- Connect CloverApps to the canonical registry and current status.
- Connect WarRoom to permitted private evidence and case state.
- Add Backup Center, Trust Center, Action Center, and owner decision cards.

Exit gate: one owner-facing window reliably shows what exists, what changed, what is blocked, and what requires a decision.

### Phase 4 — Priority application delivery

Initial value sequence:

1. Lakeside Essentials / Serenity Stores.
2. SongAndStage.
3. PropertyCare X / Booking Central / Stay Hub.
4. Boat Rentals.
5. Clover WarRoom.
6. Poolside Pulse and other mature resort tools.
7. RollinD and creative publishing systems.

The sequence can change when verified urgency, revenue, safety, legal deadlines, or owner priorities justify it.

Exit gate: each selected application has stable production journeys, monitoring, backups, documentation, and a support/rollback plan.

### Phase 5 — Continuous assisted operations

- Read-only monitoring first.
- Prioritized action queue.
- Human-only Action Cards.
- Constrained execution tools.
- Return-and-report receipts.
- Automatic status and ledger updates.

Exit gate: the system reliably detects important changes and helps complete work without broad or hidden authority.

### Phase 6 — Scale, collaboration, and showcase

- Safe collaboration with role-based access.
- Reusable app templates and standards.
- Public portfolio and project showcase separated from private operations.
- Measured revenue, reliability, user outcomes, and maintenance cost.

Exit gate: the system can expand without losing provenance, privacy, recoverability, or owner control.

## Definition of complete

The mission is not complete merely because the apps render or deploy. Completion requires:

- current and verified identity;
- core user journeys;
- appropriate UX and accessibility;
- secure data boundaries;
- deterministic validation;
- owner-reviewed production release;
- monitoring and operational documentation;
- complete backup and proven restoration;
- current registry and progress state;
- no unresolved critical safety or data-loss risk.

## Change control

This plan is versioned guidance. Future revisions must:

1. preserve prior versions;
2. state why the change is needed;
3. identify changed priorities, scope, weights, or definitions of done;
4. cite the evidence supporting status changes;
5. update the history ledger;
6. avoid treating a plan revision as production authority.

The repository is canonical for the plan. CloverApps may mirror it into a database or interface, but the mirrored representation must retain source commit and version identity.
